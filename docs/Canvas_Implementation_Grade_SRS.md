# Canvas
## Software Requirements Specification (SRS)
### Implementation-Grade Baseline for Claude Code and Codex

**Product name:** Canvas  
**Alternative branding:** The Canvas  
**Document type:** Software Requirements Specification  
**Status:** Approved baseline for implementation  
**Primary audience:** Product owner, software engineers, Claude Code, Codex, QA  
**Primary stack:** Next.js + TypeScript, PostgreSQL, object/file storage  
**Generated website target:** Next.js + TypeScript frontend-only projects  
**UI direction:** Clean, minimal, icon-led SaaS interface inspired by the usability patterns of ChatGPT, Vercel, and Resend, without copying their branding or layouts.

---

# 1. Purpose

Canvas is an AI-assisted website-building platform for non-technical users.

The product allows users to create frontend websites by organizing pages in a familiar file-explorer-style tree, describing desired pages or changes in natural language, uploading company media, defining company identity and theme settings, creating reusable building blocks, previewing changes in real time, maintaining version history, collaborating with other users, and exporting the generated website as a ZIP archive.

Canvas itself is a full-stack application. Websites generated by Canvas are frontend-only.

This document is the implementation source of truth for the first production-grade version unless a later approved requirement explicitly replaces a section.

---

# 2. Product Vision

Canvas should make website creation understandable to users who do not know HTML, CSS, JavaScript, React, routing, component architecture, or source control.

The user should think in terms of:

- My company.
- My website.
- My pages.
- My images.
- My brand.
- My reusable sections.
- What I want the AI to change.
- What the website currently looks like.
- How to undo or restore a previous state.
- How to share the project with another person.
- How to download the completed frontend.

The application should hide unnecessary technical complexity while preserving a technically sound generated project.

---

# 3. Product Principles

The implementation must follow these principles.

1. **Non-technical first**  
   The primary experience must not require code knowledge.

2. **AI-assisted, not AI-chaotic**  
   AI output must respect project context, company identity, existing pages, reusable components, and technical restrictions.

3. **Consistency by default**  
   New pages and components should look like parts of the same website.

4. **Reusable instead of repetitive**  
   Navbars, footers, cards, sections, and other building blocks should be reusable.

5. **Safe iteration**  
   Every meaningful AI change must be reversible.

6. **Project isolation**  
   Data, files, AI context, and collaborators from one project must never leak into another.

7. **Frontend-only generated output**  
   Generated websites must not silently create unsupported backend behavior.

8. **Simple UI, powerful system**  
   Advanced capabilities may exist, but the interface should expose them only when useful.

9. **Provider independence**  
   AI integration must be abstracted so the product is not permanently tied to one AI vendor.

10. **Exportable ownership**  
    Users must be able to download a usable generated project.

# 6. User Roles and Authorization

## 6.1 Authenticated User

An authenticated user can:

- Create workspaces.
- Create projects in their own workspaces.
- Access projects they own.
- Access projects they have joined as collaborators.
- Manage their account.

## 6.2 Project Owner

The Project Owner can:

- Perform all project editing actions.
- Rename the project.
- Edit company identity and project theme.
- Add, edit, move, duplicate, archive, and delete pages/folders.
- Generate or modify pages using AI.
- Create and modify building blocks.
- Manage media.
- Create invitation links.
- Revoke invitation links.
- Remove collaborators.
- Archive/delete the project.
- Create checkpoints.
- Restore versions/checkpoints.
- Export the project.

The owner must not be removable from the project through the normal collaborator-removal flow.

## 6.3 Collaborator

A Collaborator can:

- Open the project.
- View the project structure.
- Create and modify pages/folders.
- Use AI generation.
- Create and modify building blocks.
- Upload/manage project media.
- Use preview.
- Use undo/redo when valid.
- Create versions/checkpoints if permitted by the common project edit model.
- Export the project.

A Collaborator cannot:

- Remove the Project Owner.
- Remove other collaborators.
- Generate/revoke invite links.
- Archive or permanently delete the project.
- Change ownership.

## 6.4 Authorization Rule

Every server-side query and mutation must validate:

1. The authenticated user.
2. The requested workspace/project.
3. The user's effective project role.
4. The required permission for the action.

Client-side hiding of controls is not sufficient authorization.

# 7. Workspace and Project Model

## 7.1 Workspaces

- A user may own multiple workspaces.
- A workspace is isolated from other workspaces.
- A workspace can contain multiple projects.
- V1 project invitations grant access to a project, not the entire workspace.
- A collaborator may therefore access a project inside another user's workspace without gaining access to unrelated projects in that workspace.

## 7.2 Projects

Each project must include:

- Immutable internal UUID.
- Workspace UUID.
- Owner user UUID.
- Name.
- Optional description.
- Project status.
- Created timestamp.
- Updated timestamp.
- Brand/theme configuration.
- Project instructions.
- Current project state references.
- Collaboration membership.
- Media library.
- Page tree.
- Building blocks.
- AI conversation history.
- Version history.
- Export history.

## 7.3 Project Status

Supported states:

- `active`
- `archived`
- `deleted`

Archived projects remain recoverable and are hidden from the primary active-project list.

Deletion should initially be implemented as a soft-delete state. Permanent physical deletion may run later through controlled retention/cleanup logic.

# 9. Project Invitations and Collaboration

## 9.1 Invitation Link

Project Owners can generate a project invitation link.

The link:

- Grants Collaborator access after acceptance.
- Must contain an unguessable token.
- Must store only a secure hash of the token server-side.
- Must support expiration.
- Must support revocation.
- Must be regeneratable.
- Must not grant workspace-wide access.

A practical V1 default is a seven-day expiration, configurable in code/configuration.

## 9.2 Invitation Acceptance

When an unauthenticated user opens an invite:

1. Canvas preserves the invite token.
2. User signs in or creates an account.
3. Canvas validates the invite.
4. Canvas adds a project membership if not already present.
5. Canvas redirects to the project.

Repeated acceptance by an existing collaborator must be idempotent.

## 9.3 Removing Access

The Project Owner can remove a collaborator.

Removal must immediately prevent future authenticated project access.

Existing browser state must not allow continued mutations after access is removed.

## 9.4 Concurrent Editing

V1 is not Google-Docs-style collaborative editing.

Canvas must instead:

- Show that another collaborator is currently modifying a page when known.
- Prevent two AI generation jobs from mutating the same target page/block simultaneously.
- Enforce concurrency server-side.
- Use leases/locks with expiration to avoid permanent stale locks.
- Use optimistic version checks before committing generated changes.
- Reject or rebase stale mutations rather than silently overwriting newer work.

# 10. Page Tree

## 10.1 Structure

Each project has a hierarchical tree supporting:

- Pages.
- Folders.
- Nested pages.
- Nested folders.
- Reordering.
- Moving nodes.
- Renaming.
- Duplication.
- Deletion/archive.

Example:

```text
Pages
├── Home
├── About
├── Services
│   ├── Web Development
│   └── Mobile Development
├── Resources
│   ├── Guides
│   └── FAQ
└── Contact Us
```

## 10.2 Node Types

A node must have:

- UUID.
- Project UUID.
- Parent node UUID or null.
- Type: `page` or `folder`.
- Name.
- Slug where applicable.
- Sort/order index.
- Created/updated timestamps.

Pages additionally have:

- Current page version UUID.
- SEO metadata.
- Homepage flag.
- Navigation-related metadata if needed.

Folders are organizational and are not routable unless future functionality explicitly adds an index page.

## 10.3 Tree Rules

- No cycles.
- A node cannot become its own ancestor.
- Names may repeat in different branches.
- Slugs must resolve to unique final routes.
- Home page route is `/`.
- Tree mutations must preserve deterministic ordering.

# 11. URL and Slug Requirements

Canvas automatically creates clean page slugs.

Example:

- Page name: `Contact Us`
- Default slug: `contact-us`
- Route: `/contact-us`

Nested example:

- `Services`
- `Web Development`
- Route: `/services/web-development`

## 11.1 Rules

- Slugs are editable.
- Slugs are not database primary keys.
- Page UUIDs remain immutable.
- Renaming a page does not destroy history.
- Changing a slug does not create a new page identity.
- Invalid URL characters must be normalized.
- Conflicting routes must be rejected with a clear validation error.
- Route computation must be deterministic.
- User-defined slugs should not be silently overwritten after creation.

# 13. AI Prompting

## 13.1 Page Creation

When a user creates/selects a page and asks AI to generate it, Canvas must provide the AI with the relevant project context.

Example:

> Create a professional services page showing our three service categories and use the same navbar and footer as the rest of the website.

## 13.2 Page Modification

AI should modify existing implementation rather than regenerate the page unnecessarily.

Example requests:

- Make the hero smaller.
- Change the cards to three columns.
- Replace the text but keep the design.
- Use the image from the Media Library.
- Add the global footer.
- Make this page match the home page.

## 13.3 Element-Level Editing

Users can select a visible element/section in preview.

Canvas must maintain a stable mapping between preview elements and generated source/component identity.

A request such as:

> Make this card more compact.

must apply to the selected target, not unrelated page regions.

Implementation guidance:

- Assign stable internal Canvas node/component identifiers.
- Render them as safe preview-only metadata such as `data-canvas-id`.
- Maintain a source/manifest mapping.
- Strip Canvas-only metadata during export.

## 13.4 AI Conversation History

Canvas stores AI conversation history at project/page context.

At minimum store:

- User prompt.
- Target project.
- Target page/block if applicable.
- Selected media references.
- Selected element reference if applicable.
- AI response summary.
- Generation job.
- Resulting Change Set.
- Timestamp.
- Actor user.

This history supports iterative prompting.

# 14. Project Context / AI Memory Layer

This is a mandatory core system.

The AI must not operate using only the latest prompt.

## 14.1 Context Inputs

Relevant context includes:

- Company name.
- Company description/identity.
- Brand assets.
- Logo.
- Theme colors.
- Light/dark tokens.
- Radius.
- Spacing.
- Shadows.
- Font scale.
- Border thickness.
- Persistent project instructions.
- Existing page tree.
- Current page path.
- Existing active page source.
- Existing building blocks.
- Global building blocks.
- Current selected element.
- Selected media.
- Relevant recent conversation history.
- Existing route structure.
- Existing navigation.
- Technical generation constraints.

## 14.2 Context Isolation

AI context assembly must be strictly project-scoped.

Never include:

- Another project's pages.
- Another project's media.
- Another project's prompts.
- Another project's brand identity.
- Another project's source code.

## 14.3 Context Precedence

Use this precedence:

1. Platform safety/security/technical constraints.
2. Explicit current user request.
3. Persistent project instructions.
4. Project brand/theme configuration.
5. Existing global building blocks.
6. Current page/block state.
7. Relevant project history.
8. General generation defaults.

A normal page prompt must not silently rewrite project-wide brand settings. Project-wide changes should be explicit.

## 14.4 Token/Context Budgeting

Large projects must not dump all source code into every prompt.

The context system should select the smallest relevant subset based on:

- Current page.
- Referenced pages.
- Used global components.
- Requested operation.
- Current navigation.
- Relevant media.
- Relevant recent history.

Summaries/manifests may be used for unrelated project sections.

- Primary.

### Spacing
Controls the general density/spacing scale.

### Shadows
Controls shadow strength/presence.

### Font Scale
Controls overall typography scale.

### Border Thickness
Controls general border weight.

Changing theme settings should update generated previews wherever components use shared theme tokens.

AI should prefer project tokens over one-off hardcoded values.

# 19. Media Library

V1 supports images only.

## 19.1 Media Structure

Users can create folders similar to a simple Google Drive/file browser.

Example:

```text
Media
├── Logos
│   ├── logo.png
│   └── logo-white.png
├── Team
│   ├── ahmed.jpg
│   └── sara.jpg
└── Products
    ├── product-a.jpg
    └── product-b.jpg
```

## 19.2 Required Operations

- Create folder.
- Rename folder.
- Move folder.
- Delete folder.
- Upload image.
- Rename image.
- Move image.
- Delete image.
- Browse/search images.
- Attach image to AI prompt.

## 19.3 Storage

Binary media must not be stored directly in PostgreSQL.

Use object/file storage.

PostgreSQL stores metadata such as:

- UUID.
- Project UUID.
- Folder UUID.
- Original filename.
- Stored object key.
- MIME type.
- File size.
- Width.
- Height.
- Optional alt text.
- Created by.
- Created timestamp.

## 19.4 Supported Formats

V1 should support:

- PNG.
- JPEG/JPG.
- WEBP.
- SVG only if securely sanitized before use.

Recommended maximum upload size: 10 MB per image, configurable.

## 19.5 Asset References

Generated page source should use logical/managed media references rather than temporary signed URLs.

The export pipeline resolves media references into local exported assets.

## 19.6 Deletion Integrity

Media referenced by current or historical versions must not be physically destroyed in a way that makes history unrestorable.

Soft deletion and background garbage collection are preferred.

# 22. Live Preview

## 22.1 Requirements

The Preview:

- Shows the active project state.
- Updates after validated AI changes.
- Supports normal page navigation.
- Supports desktop/tablet/mobile/full-screen modes.
- Supports selectable elements for targeted AI editing.
- Must display user media correctly.
- Must not require a full browser page reload for every normal project change where avoidable.

## 22.2 Real-Time Behavior

When AI generates or modifies content:

1. Show generation progress.
2. Validate generated changes.
3. Apply validated changes to a temporary/current project state.
4. Refresh the preview as soon as a valid update is available.
5. Show a change summary.
6. Enable Undo for the committed change.

Do not execute incomplete or unvalidated arbitrary partial code merely to appear more real-time.

---

# 23. Preview Security

Generated code is untrusted.

It must never run with direct access to authenticated Canvas application state.

Requirements:

- Preview runs in an isolated iframe or isolated origin.
- Preview cannot read Canvas authentication cookies.
- Preview cannot access Canvas localStorage/sessionStorage.
- Use a restrictive Content Security Policy.
- Do not use `allow-same-origin` with unsafe combinations unless an isolated origin makes it safe.
- Prevent generated source from invoking internal Canvas APIs.
- Arbitrary external network calls from generated code are prohibited by default.
- Generated code must not access `process.env` secrets.
- Generated code must not execute Node.js filesystem/process APIs.
- Generated code must not introduce arbitrary remote scripts.
- Generated code must not use `eval` or `new Function`.
- `dangerouslySetInnerHTML` should be blocked unless content is explicitly sanitized by platform-controlled logic.

This boundary is mandatory.

# 24. Generated Website Technical Target

Canvas-generated projects must use:

- Next.js.
- TypeScript.
- React.
- Static/frontend-compatible architecture.

Recommended V1 styling implementation:

- Tailwind CSS.
- Shared CSS variables/design tokens for theme consistency.

## 24.1 Frontend-Only Constraint

Generated projects must not include:

- API routes.
- Route handlers.
- Server actions.
- Database clients.
- Secret environment variables.
- Authentication backend.
- Server-side payment logic.
- Server-only SDKs.
- Background workers.

Client-side interactivity is allowed.

Examples:

- Accordion.
- Tabs.
- Carousel.
- Mobile navigation.
- Modal.
- Local filtering.
- Form validation.
- Client-side state.

## 24.2 Fake Backend Prevention

If the user asks for a feature requiring a backend, Canvas must not pretend that the backend exists.

Example:

> Build a login page.

Allowed:
- Login UI.
- Form fields.
- Client-side validation.

Not allowed:
- Claiming that real authentication works.

The AI/change summary should indicate when a requested capability is visual-only because generated sites are frontend-only.

# 25. Generated Code Rules

Generated code must follow a controlled dependency and import model.

## 25.1 Allowlist

Canvas should maintain an allowlist for packages available to generated projects.

The AI must not invent arbitrary npm dependencies.

The initial allowlist should include only dependencies necessary for the supported generated frontend stack.

## 25.2 Code Validation

Before generated changes become active:

- Parse source.
- Validate syntax.
- Validate imports.
- Validate dependency allowlist.
- Type-check affected project/generated source.
- Enforce prohibited API rules.
- Validate route collisions.
- Validate referenced media.
- Validate referenced global blocks.
- Validate export compatibility.

A failed validation must leave the previously active version intact.

## 25.3 Code Quality

Generated source should favor:

- Reusable components.
- Semantic HTML.
- Accessible labels.
- Consistent project theme tokens.
- Clear component names.
- Minimal duplication.
- No dead dependencies.
- No embedded secrets.
- No arbitrary inline styles when shared tokens are suitable.

# 27. Autosave

Canvas must autosave normal project metadata changes.

Examples:

- Project name.
- Page name.
- Slug.
- Page order.
- Theme settings.
- Project instructions.

Autosave should:

# 28. Version Control Model

Version control is an in-app Canvas feature.

It is not exposed as Git to non-technical users.

## 28.1 Page Identity

Do not use the page name as the primary key.

Use:

- `page_id` = immutable UUID.
- `name` = editable.
- `slug` = editable.
- `current_version_id` = active immutable version.

## 28.2 Page Versions

Every meaningful generated page change creates a new immutable version.

A page version should store:

- UUID.
- Page UUID.
- Version number.
- Generated source.
- Structured metadata/manifest.
- Created by user.
- Generation job UUID.
- Change Set UUID.
- Created timestamp.

Historical versions must never be overwritten.

## 28.3 Restoring a Page Version

Restoring an older page version:

- Must not delete newer history.
- Sets/restores an active state through a new restore Change Set or active-version pointer operation.
- Must be auditable.
- Must be reversible where possible.

---

# 29. Change Sets

One AI request may affect multiple entities.

Example:

> Add Careers to our global navbar and create the Careers page.

This may change:

- Page tree.
- New Careers page.
- Global Navbar block.

These changes belong to one Change Set.

A Change Set should contain:

- UUID.
- Project UUID.
- Actor user UUID.
- Prompt/message UUID.
- Summary.
- Created timestamp.
- Operation type.
- Before references.
- After references.
- Reversible flag.

---

# 30. Undo and Redo

## 30.1 Undo

Undo applies to the latest compatible reversible Change Set.

Undo must:

- Restore previous active references/settings.
- Preserve immutable history.
- Record the undo action.
- Update preview immediately after the restore.
- Not remove historical versions.

## 30.2 Redo

Redo reapplies the most recently undone compatible Change Set.

## 30.3 Collaboration Conflict Rule

If another collaborator has changed the same affected entities after the user's reversible Change Set, blind Undo/Redo must not overwrite that newer work.

Canvas should instead:

- Disable direct Undo/Redo for that conflicting operation.
- Explain that newer changes exist.
- Direct the user to Version History/Checkpoint restore.

---

# 31. Named Checkpoints

Users can create named checkpoints.

Examples:

- Before client review.
- Homepage approved.
- Before rebrand.

A checkpoint stores project-wide active references, including where applicable:

- Current page versions.
- Current building block versions.
- Theme/settings revision.
- Project instruction revision.
- Tree state.
- Relevant media references.

Checkpoints are immutable records.

---

# 32. Project-Level Restore

Canvas must support restoring a project to a checkpoint or project-level saved state.

This is required because one AI request may modify several pages/components/settings.

Project restore must:

- Preserve history.
- Restore active references.
- Create an auditable restore operation.
- Validate the restored project.
- Refresh preview.

---

# 33. AI Change Summary

After every successful AI Change Set, show a concise summary.

Example:

```text
Updated:
- Hero section layout
- Added uploaded office image
- Changed CTA button
- Updated mobile spacing
```

The summary should also identify:

- New pages.
- Global-component changes.
- Theme changes.
- Visual-only limitations.
- Validation warnings.

---

# 34. Page Duplication

Users can duplicate a page.

Duplication must:

- Create a new Page UUID.
- Copy the current active content into a new initial version.
- Create a new non-conflicting name.
- Create a new non-conflicting slug.
- Preserve referenced building blocks/media by reference where safe.
- Not share future page version history with the source page.

---

# 35. Building-Block Duplication

Users can duplicate a building block.

Duplication must:

- Create a new block UUID.
- Copy the current active version into a new initial version.
- Give it a non-conflicting name.
- Not share future version history with the source block.

---

# 36. SEO and Page Metadata

Each page must support:

- Page name.
- URL/slug.
- Page title.
- Meta description.

AI may suggest page title and meta description.

Users can override suggestions.

Export must include the metadata in the generated page.

---

# 37. Interactive Preview Navigation

Previewed website navigation should function like a real site.

Requirements:

- Clicking internal links navigates within the project preview.
- Route changes reflect active page routes.
- Navigation must not leave the Canvas editor unexpectedly for internal links.
- External links may open safely in a separate browser context.

# 38. Export

## 38.1 Primary Format

V1 export format is ZIP.

RAR is out of scope.

## 38.2 ZIP Contents

The ZIP should contain a runnable generated frontend project, including:

- Next.js project structure.
- TypeScript source.
- Page routes.
- Reusable components.
- Global components.
- Theme/design tokens.
- Public media assets.
- Styles.
- `package.json`.
- Required configuration.
- README with local run/build instructions.

Do not include:

- Canvas internal IDs unless required by generated app behavior.
- Canvas authentication data.
- Canvas project tokens.
- AI provider secrets.
- Temporary signed URLs.
- Internal database IDs where avoidable.
- Server-side Canvas code.

## 38.3 Static Compatibility

Generated project should be compatible with static/frontend-only deployment where practical.

---

# 39. Export Validation

Before providing the ZIP, Canvas must validate:

- All required pages exist.
- Routes are unique.
- Referenced media exists.
- Referenced global blocks exist.
- No prohibited imports.
- No unsupported backend code.
- Type-check passes.
- Build passes.
- Internal links resolve where detectable.
- Exported files contain no Canvas secrets.

If validation fails:

- Do not label the export as successful.
- Show clear validation failures.
- Preserve the project.
- Allow the user to ask AI to fix export problems.

# 40. AI Provider Abstraction

Canvas must not bind domain logic directly to one AI SDK.

Define an internal provider-independent contract.

Conceptually:

```text
AIProvider
- generatePage(...)
- modifyPage(...)
- generateBlock(...)
- modifyBlock(...)
- planChangeSet(...)
- summarizeChanges(...)
```

The exact method names are implementation details.

Requirements:

- Provider selected by server configuration.
- Domain services depend on the abstraction.
- Provider-specific SDK types must not leak into core domain models.
- Prompt assembly should be provider-independent.
- Provider failures should return normalized errors.
- Token/usage metadata may be stored for observability.

At least one provider adapter is required for functional development, but provider choice is a deployment configuration decision and may be changed without rewriting Canvas domain logic.

# 41. AI Generation Job Model

A generation job should include:

- UUID.
- Project UUID.
- Actor user UUID.
- Target type.
- Target UUID.
- Prompt/message UUID.
- Status.
- Progress stage.
- Started timestamp.
- Finished timestamp.
- Error code/message.
- Resulting Change Set UUID.
- Provider usage metadata if available.

Suggested statuses:

- `queued`
- `preparing_context`
- `generating`
- `validating`
- `applying`
- `completed`
- `failed`
- `cancelled`

## 41.1 Progress

UI should show meaningful progress without exposing provider internals.

## 41.2 Cancellation

If supported by the provider/job runner, a user should be able to cancel an active generation before commit.

A cancelled/failed generation must not replace the active valid page.

# 45. Database Integrity Requirements

- All tenant-owned records must contain or derive a project/workspace boundary.
- Foreign keys must enforce valid ownership relationships.
- Route uniqueness must be enforced through application validation and database constraints where practical.
- Duplicate project membership must be impossible.
- Version numbers must be unique within their entity.
- Active current-version pointers must reference versions belonging to the same page/block.
- Cross-project media/block references must be rejected.
- Soft-deleted records must not appear in normal active queries.
- Tree cycles must be prevented.
- Transactions must be used for multi-entity Change Set commits.

# 49. Performance Requirements

These are target values, not reasons to compromise data integrity.

## 49.1 Normal Application Operations

Target:

- Common non-AI API actions: p95 under 500 ms excluding network variance.
- Autosave acknowledgement: normally under 1 second.
- Project navigation should feel immediate after initial load.

## 49.2 AI Operations

AI generation duration depends on the provider.

Requirements:

- User receives immediate job/progress feedback.
- UI must not appear frozen.
- Long-running requests must not block unrelated project navigation.
- User may continue browsing other pages/projects while generation runs.

## 49.3 Preview

## 50.1 General

- User-readable.
- Logged with internal context.
- Non-destructive.
- Recoverable where possible.

- Job status becomes failed.

- Show failures.

# 51. Security Requirements

## 51.1 Multi-Tenant Isolation

Every project-scoped action must prevent horizontal privilege escalation.

## 51.2 Input Validation

Validate all:

- Names.
- Slugs.
- IDs.
- Prompt references.
- Uploaded file types.
- File sizes.
- Invite tokens.
- Theme values.
- AI output.

- Sanitize SVG.
- Prevent path traversal.

## 51.5 Secrets

- Database credentials.
- Session signing keys.

```text
Syntax/Type/Import Validation
   ↓
Route/Media/Block Validation
   ↓
Preview/Build Validation
   ↓
Create Immutable Versions
   ↓
Commit Change Set Transaction
   ↓
Update Active References
   ↓
Release Lease
   ↓
Refresh Preview
   ↓
Show Change Summary + Undo
```

A generation provider must never directly mutate the production database.

---

# 60. Structured AI Change Contract

AI output should be structured enough for Canvas to know what is being changed.

The implementation should avoid accepting an opaque full-project blob without target identity.

Examples of logical operations:

- Create page.
- Update page source.
- Create block.
- Update block source.
- Use existing block.
- Update navigation.
- Update page metadata.
- Attach media reference.
- Create project-level change plan.

The exact JSON schema is an implementation detail, but it must be validated server-side before use.

---

# 61. Preview Manifest

Canvas should maintain a generated manifest describing the active project.

Example concepts:

- Route -> page UUID/version.
- Component/block UUID -> active version.
- Media UUID -> preview asset URL.
- Theme tokens.
- Navigation structure.
- Canvas editable element IDs.

The manifest supports:

- Fast preview.
- Element selection.
- Export assembly.
- Validation.
- AI context.

---

# 62. Global Component Propagation

Global components must not be copied independently into every page.

Recommended behavior:

- Pages reference a stable global block UUID.
- Preview resolves the block's current version.
- Export resolves/copies the current global implementation into a shared component file.
- Updating the block changes all active usages.
- Historical page versions retain enough reference information to restore the correct project state using project checkpoints/change sets.

---

# 63. Data Retention and History Integrity

Version history is a core feature.

Therefore:

- Historical source versions must be immutable.
- Media required by historical versions should remain retrievable while referenced.
- Restores should create new auditable state transitions rather than destroying later versions.
- Background cleanup must respect references.
- Deleting a project must not immediately destroy data required for accidental-deletion recovery.

Exact retention duration for permanently deleted projects may be configured later.

# 66. Acceptance Criteria by Major Feature

## 66.1 Project Creation

**Given** an authenticated user  
**When** they create a project  
**Then** Canvas creates an isolated project with a UUID, owner membership, default theme, empty page tree, and empty media/block libraries.

## 66.2 AI Page Generation

**Given** a project page and project context  
**When** the user submits a generation prompt  
**Then** Canvas creates a tracked generation job, validates output, creates an immutable page version, activates it only after validation, refreshes preview, and offers Undo.

## 66.3 Theme Consistency

**Given** project brand/theme settings  
**When** AI generates a new page  
**Then** the page uses shared project design tokens and existing relevant global components unless explicitly instructed otherwise within allowed constraints.

## 66.4 Media

**Given** an uploaded project image  
**When** the user attaches it to a generation prompt  
**Then** AI may use the image in the generated page and export resolves it to a local asset.

## 66.5 Version Restore

**Given** several page versions  
**When** the user restores an older version  
**Then** newer versions remain in history and the restored content becomes the active state through an auditable restore action.

## 66.6 Collaboration

**Given** a valid invitation link  
**When** an authenticated user accepts it  
**Then** they gain Collaborator access only to that project.

## 66.7 Access Revocation

**Given** an existing collaborator  
**When** the owner removes them  
**Then** subsequent project reads/mutations are denied.

## 66.8 Export

**Given** a valid project  
**When** the user exports it  
**Then** Canvas validates and produces a ZIP containing a runnable Next.js + TypeScript frontend without Canvas secrets or backend code.

# 70. Implementation Rules for Claude Code and Codex

When implementing this SRS:

1. Treat this document as the product source of truth.
2. Do not remove or weaken requirements to simplify implementation without explicit approval.
3. Implement in phases.
4. Reuse components and services.
5. Keep UI, domain logic, persistence, AI provider, storage provider, preview runtime, and export logic separated.
6. Do not place authorization only in UI.
7. Do not allow generated code to execute in the authenticated Canvas shell.
8. Do not let the AI provider mutate the database directly.
9. Do not activate unvalidated generated source.
10. Keep page/block versions immutable.
11. Use UUIDs for domain identity.
12. Do not use page names as primary keys.
13. Do not bind domain logic to a single AI vendor.
14. Do not bind media domain logic to a single object-storage vendor.
15. Generated websites remain frontend-only.
16. ZIP is the primary export.
17. Do not add publishing/hosting in V1 unless explicitly approved.
18. Do not implement Google-Docs-style live editing in V1.
19. Use reusable UI components and consistent system-wide patterns.
20. Keep the Canvas application UI simple for non-technical users.
21. Add tests with every major feature instead of postponing all testing.
22. Preserve all project/tenant boundaries in tests and queries.
23. Keep migrations deterministic and reviewable.
24. Avoid premature microservices. Keep clean boundaries so services can be extracted later.
25. Do not expose technical jargon in primary non-technical user flows.

Canvas is a full-stack SaaS application that allows non-technical users to build frontend websites through AI.

- Workspaces and projects.
- File-explorer-style page organization.
- Clean page URLs.
- AI page generation and modification.
- Company identity and centralized themes.
- Reusable and global building blocks.
- Image media management.
- Project-aware AI context/memory.
- Safe live preview.
- Responsive generation.
- Element-level AI editing.
- Autosave.
- Undo/Redo.
- Immutable version history.
- Named checkpoints.
- Project restore.
- Collaboration by invite link.
- Read-only code inspection.
- Validated ZIP export.
